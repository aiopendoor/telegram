# 체계적 디버깅 (Systematic Debugging)

## 개요

무작위적인 수정은 시간을 낭비하고 새로운 버그를 만듭니다. 빠른 패치는 근본적인 문제를 가릴 뿐입니다.

**핵심 원칙:** 수정을 시도하기 전에 **반드시** 근본 원인(Root Cause)을 찾으십시오. 증상만 고치는 것은 실패입니다.

---

## 철칙 (The Iron Law)

```
근본 원인 조사 전에는 어떤 수정도 하지 마십시오.
```

1단계를 완료하지 않았다면 수정을 제안할 수 없습니다.

## 사용 시점

다음과 같은 모든 기술적 문제에 사용하십시오:
- 테스트 실패, 운영 버그, 예상치 못한 동작, 성능 문제, 빌드 실패, 통합 이슈 등.

**특히 다음과 같은 상황에서 반드시 사용하십시오:**
- 시간 압박이 있을 때 (응급 상황일수록 추측의 유혹이 강해집니다)
- "금방 고칠 수 있을 것 같다"고 느껴질 때
- 이미 여러 번 수정을 시도했지만 효과가 없었을 때
- 문제의 원인을 완전히 이해하지 못했을 때

---

## 4단계 프로세스

각 단계를 반드시 완료한 후 다음 단계로 넘어가십시오.

### 1단계: 근본 원인 조사 (Root Cause Investigation)

**수정을 시도하기 전에:**
1. **에러 메시지를 주의 깊게 읽기**: 스택 트레이스, 파일 경로, 에러 코드를 끝까지 확인하십시오.
2. **일관되게 재현하기**: 문제를 신뢰할 수 있게 트리거할 수 있는지, 정확한 단계는 무엇인지 확인하십시오.
3. **최근 변경 사항 확인**: 무엇이 바뀌었는지(Git diff, 의존성, 설정 등) 확인하십시오.
4. **증거 수집**: 다중 계층 시스템인 경우 각 경계에서 로그를 남겨 어디서 부러지는지 확인하십시오.
5. **데이터 흐름 추적**: 잘못된 값이 어디서 시작되었는지 거꾸로 추적하십시오.

### 2단계: 패턴 분석 (Pattern Analysis)

1. **정상 작동 예시 찾기**: 같은 코드베이스 내에서 유사하지만 정상적으로 작동하는 코드를 찾으십시오.
2. **참조 문헌과 비교**: 적용하려는 패턴의 공식 문서나 구현 사례를 꼼꼼히 읽으십시오.
3. **차이점 식별**: 정상인 것과 고장난 것의 차이를 사소한 것까지 모두 나열하십시오.

### 3단계: 가설 수립 및 테스트 (Hypothesis and Testing)

1. **단일 가설 수립**: "Y이기 때문에 X가 근본 원인이라고 생각한다"고 명확히 기술하십시오.
2. **최소한의 테스트**: 가설을 검증하기 위해 가장 작은 단위로 변경하고 테스트하십시오.
3. **검증**: 가설이 맞았는지 확인하고, 틀렸다면 새로운 가설을 세우십시오.

### 4단계: 구현 (Implementation)

1. **실패하는 테스트 케이스 생성**: 수동 확인이 아닌 자동화된 테스트(TDD)를 먼저 만듭니다.
2. **단일 수정 적용**: 식별된 근본 원인만 해결합니다. "간 김에 고치는" 추가 수정은 하지 마십시오.
3. **수정 확인**: 테스트가 통과하는지, 다른 문제는 없는지 최종 확인합니다.

---

## 3회 이상 실패 시: 아키텍처 의심

수정을 3번 이상 시도했는데도 해결되지 않는다면, 이는 단순 버그가 아니라 **아키텍처의 문제**일 확률이 높습니다.

- 각 수정이 다른 곳에서 새로운 문제를 일으키는 경우
- 수정을 위해 너무 많은 리팩토링이 필요한 경우
- 근본적인 패턴 자체가 신뢰할 수 없는 경우

이 경우 수정을 중단하고 사용자(파트너)와 근본적인 접근 방식에 대해 논의하십시오.

---

## 금지 사항 (Red Flags)

다음과 같은 생각이 든다면 즉시 멈추고 1단계로 돌아가십시오:
- "일단 고치고 나중에 조사하자"
- "X를 바꿔보고 어떻게 되는지 보자 (추측성 수정)"
- "원인은 잘 모르겠지만 이렇게 하면 될 것 같다"
- **"한 번만 더 고쳐보자" (이미 2번 이상 실패했을 때)**

## 요약

| 단계 | 주요 활동 | 성공 기준 |
|-------|---------------|------------------|
| **1. 근본 원인** | 에러 읽기, 재현, 변경 확인, 증거 수집 | 무엇이, 왜 고장 났는지 이해함 |
| **2. 패턴 분석** | 정상 예시 찾기, 비교 | 차이점을 식별함 |
| **3. 가설 수립** | 이론 수립, 최소 테스트 | 가설이 검증됨 |
| **4. 구현** | 실패 테스트 생성, 수정, 확인 | 버그 해결, 테스트 통과 |
